# Sales Call Tracker - Decision Log


- **Decision 1:** The post-call outcome buttons can never both be on. In the shared popup used by the keypad, automated, and My List flows alike, Interested and Do not call again are mutually exclusive: tapping one clears the other, and tapping the chosen one again unchecks it — the popup allows both off or exactly one on, never both on. The popup is one mergeable piece of code used everywhere; the only flow-specific extra is the "Go to next call" checkbox, which the automated and My List popups carry and the keypad popup does not. The two flags and the note still ride the sync batch exactly as before.

- **Decision 2:** The My List tab shows KPIs only, exactly as its approved screen: the Upload, Download, and Clear buttons, Start Calling, the four summary cards — Left, Called, Interested, Do not call — and the line that the list lives only on the phone. The per-number rows, their badges, and the screen's list-loading code are removed. The `my_list_numbers` table itself stays: Start Calling, Download, Clear, and call-marking still run on it, and upload works exactly as before.

- **Decision 3:** One shared direct-call flow serves every list row. It writes the intent row, places the call straight through Android's direct-call intent with CALL_PHONE, and runs the shared post-call popup after — the exact keypad process. Tapping a History row or its call button dials the number directly instead of filling the keypad; the Scheduled rows' call button uses the same flow; the keypad itself is unchanged. With CALL_PHONE denied, the flow falls back to the standing rule — the number goes to the phone's own dialer and the call is not tracked.

- **Decision 4:** The Scheduled tab's rows gain a call button beside Copy and WhatsApp. Tapping WhatsApp on a row removes that booking from the list — the salesperson handled it. Tapping call dials through the shared direct-call flow: the recorded call removes the row, and the post-call popup's answer overwrites the booking — "Do not schedule" leaves it removed, and a new schedule replaces the old booking with the new date. The 24-hour removal window and the Due badge stay exactly as they are.

- **Decision 5:** The My List post-call popup gains the same Schedule choice the automated flow has — same popup, same pieces. Choosing Schedule books the number as a keypad-style booking keyed by phone number, so it appears on the Scheduled tab with Copy, WhatsApp, and the call button, and it leaves that tab by the same rules as any booking.

- **Decision 6:** The WhatsApp First message setting defaults ON with the text "Hello sir, Mai Apex Album AI se baat kar raha/rahi hu" — a fresh install opens every WhatsApp chat with that line pre-typed. A phone that already saved its own first-message choice keeps what it saved. The text stays editable in Settings, WhatsApp always lets the salesperson edit before sending, and nothing ever sends by itself.

- **Decision 7:** Three Settings cleanups together: the Do-not-track screen's add button becomes a bare + icon in the header with no text, because the old texted button did not fit on mobile; leaving the Settings tab always resets it, so coming back lands on the Settings home and never inside a sub-page like WhatsApp or Do-not-track; and the "Local data" section header is removed because the settings list holds several kinds of rows now — the "Clear local data" row itself keeps its name and behavior unchanged.

- **Decision 8:** My Stats shows the office timing in very short form — like "10 to 7" — beside the "Last 30 days" heading. The server computes the label from the stored window: 12-hour clock, minutes shown only when they are not :00, no AM/PM. The label arrives with every My Stats fetch, so it follows whatever window the manager last saved.

- **Decision 9:** The calls-by-hour chart loses its extra bar. The bars run from the window's start hour through the hour before its end — nine bars for a 10-to-7 window, labeled 10, 11, 12, 1 through 6. A call starting in hour H counts in the bar labeled H, and a call starting exactly at the window's end minute counts in the last bar, so no kept call goes missing from the chart. The buckets are computed on the backend, so My Stats and the manager dashboard change together.

- **Decision 10:** The phone's History keeps only calls the dashboard would count, and no settings endpoint opens to salespeople — the office-hours GET stays manager-only. The window reaches the phone inside responses it already receives: the login response carries it beside the token, and every My Stats fetch returns it with its short label. The app stores the window it last received; a call whose IST start minute falls outside that window never gets a history row — checked at the same moment the Do-not-track check runs — and the first-open backfill and every sweep apply the same filter. With no window received yet the phone uses the documented default, 10:00–19:00 IST. History rows already stored stay untouched.
