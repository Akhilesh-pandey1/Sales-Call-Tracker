# Sales Call Tracker - Decision Log

- **Decision 1:** The scheduled-call reminder is a local Android notification — no server push and no server job. The app uses **@notifee** (the maintained React Native local-notification library). The moment a booking is made (the post-call popup Submit that carries a schedule), the app sets one exact alarm for that lead. At the booked time the phone itself shows "Time to call" with the lead's number. Tapping the notification opens the app straight onto the booked lead's card — number and Call button ready. One notification per booked lead; it never repeats.
- **Decision 2:** Reminder alarms are rebuilt at every app open from the phone's own SQLite store, so reminders survive a phone reboot with no server call and no endpoint. Submitting a call to the booked number cancels that lead's alarm, matched by normalized number. Accepted noise, on the record: if another salesperson calls the booked number early, a stale nudge can fire — tapping it opens the app, where the due-own-booking-first rule serves the right work.
- **Decision 3:** The reminder's only permission ask is Android 13+ POST_NOTIFICATIONS, asked once at the first booking. Declined: bookings keep working, no reminders fire, and nothing nags. The tracking red banner is untouched and stays exactly as it is. Exact timing uses Android's exact-alarm capability when the phone allows it; a phone that blocks exact alarms receives the reminder a few minutes late — no user setup either way.
- **Decision 4:** A booking expires: when a lead is still `waiting` and its booking is more than `SCHEDULE_EXPIRE_HOURS = 24` hours past its time, the server frees it back to the pool — `scheduled_at` and `scheduled_by` cleared, attempt count untouched. The check runs the lazy way, before serving any lead (the same pattern as the 10-minute claim, `CLAIM_MINUTES`): expired bookings are freed first, then the serve picks. No cron and no background job. The manager's Scheduled count on the Leads page drains by itself, and a deactivated person's stuck bookings return to the pool through the same rule — no lead is stranded. This replaces the old rule that a booked lead stays reserved until it is called — a stuck booking no longer waits forever.
- **Decision 5:** A future booking locks the lead to its owner. When another salesperson dials the booked number and submits a schedule, the call is always saved, but the schedule is refused — the lead keeps the owner's booking, and the sync response lists the refused call's id in `schedule_refused_call_ids` so the app shows the toast "This lead is already booked by someone else." The owner re-books their own lead freely — a new time replaces the old. A `done` or `stopped` lead has no active booking, so anyone may book it (it lifts back to `waiting` owned by the scheduler). After the 24-hour expiry the lead is free for anyone again. This replaces the old rule that the newest schedule wins and a keypad schedule could transfer a booking from one salesperson to another — a booking now never moves between people.
- **Decision 6:** Incoming calls and calls made outside the app are tracked by ONE mechanism: at every app open, the app sweeps Android's call log and reads every INCOMING and OUTGOING entry newer than the sweep line — whatever dialer made the call. The sweep inserts a local row for each new call, and those rows ride the normal batch push to the server. No Kotlin, no caller-ID role, no new permission — Truecaller stays exactly as it is. Incoming calls are recorded ANSWERED only: a missed or rejected call is never recorded. Incoming calls never resolve leads and never burn attempts.
- **Decision 7:** Dedupe is the table itself: the sweep skips any log entry that matches an existing row — synced or pending — by normalized number inside the match window, so a call dialed from our own dialer is never counted twice. The sweep line (`last_swept_at`) defines the read window and moves in the SAME SQLite transaction that inserts the sweep's rows — the app can never crash between saving rows and moving the line. The first-ever sweep starts at the install moment — nothing historical uploads.
- **Decision 8:** The phone's tracking state lives in SQLite in three tables. `pending_calls` is extended with `direction` (`outgoing` / `incoming`) and a synced marker: a successful sync MARKS the row instead of deleting it — the marked row proves the server has the call. `do_not_track` holds the salesperson's excluded numbers (normalized number only — no names are stored) — local only, never synced, checked by the sweep BEFORE inserting in BOTH directions, so a listed number never counts as work in any direction — no dial, no minute, no active day. `sweep_state` is a one-row table holding `last_swept_at`. This replaces the old single-table rule and the delete-on-200 rule.
- **Decision 9:** The `do_not_track` number is stored in E.164 (`+919876543210`). The salesperson may type 10 digits — the app normalizes on save with the same libphonenumber-js call and the login country used everywhere else, and the sweep normalizes call-log numbers the same way, so any format typed always matches the log.
- **Decision 10:** Cleanup runs at every successful push: synced rows whose call time is behind the sweep line are deleted, so the table stays tiny. One guard makes it safe — a synced row is never deleted while its call time is still inside the sweep window, so the sweep can never meet a deleted entry again and count it twice. Three days is the worst-case backstop for anything still sitting; the server refuses calls older than that anyway.
- **Decision 11:** The server changes: the `calls` table gains a `direction` column (`outgoing` / `incoming`; existing rows are `outgoing`), sync items carry an optional `direction`, and the office-hours gate applies identically to both directions — the app never filters by time, the server keeps only calls starting inside office hours and drops the rest. Incoming calls never resolve leads and never burn attempts. The salesperson's app gets no incoming call list — only the do-not-track list in Settings and the new My Stats pieces below.
- **Decision 12:** Offline changes nothing: swept calls wait in SQLite and ride the next successful push, exactly like dialed calls. Sweep, push, and cleanup all run while the app is in the foreground — no background jobs.
- **Decision 13:** Minutes mean TOTAL talk — outgoing + incoming — everywhere the word appears: the Talk minutes card, the team page rows, the performance table's Minutes column, and Top 5 by minutes. Dials, Connected, Not connected, Connected %, and Active days stay outgoing-based, now counting dials made outside the app too. Active days count only days with at least one outgoing work call — answering an incoming call alone never makes a day active, and do-not-track numbers never make one. The incoming/outgoing split is visible in exactly one place per person: the donut chart with its numbers line.
- **Decision 14:** The salesperson's My Stats keeps its four KPI cards — Avg minutes now holds total talk per active day — and its four-column performance table, whose Minutes column now holds total talk. A new donut chart shows incoming vs outgoing as a share of total talk minutes, with the same Today / Yesterday / 30 days switch, and one line under it carries the exact numbers — "Outgoing 142 calls · 310 min — Incoming 37 calls · 52 min". The calls-by-hour chart becomes ONE stacked bar per hour: total height is all calls that hour, two color segments (outgoing, incoming) sized by share, counts written inside the segments; the best-hour highlight follows total calls. The server computes every percentage and total; the phone only draws.
- **Decision 15:** The manager's web follows the same rule as My Stats: Talk minutes on the dashboard is total talk; the hour chart is the same stacked bars with the split in its summary line ("142 outgoing · 37 incoming"); Top 5 people rank by total talk minutes; team rows keep dials · connected · minutes with minutes as total talk. The person view uses the same person endpoint as My Stats, so it looks identical by construction. The Leads and Accounts pages are untouched.
