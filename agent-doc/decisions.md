# Sales Call Tracker - Decision Log
- **Decision 1:** The core pain is the manager's: with 15-20 sales people, the manager has no visibility into who is making calls, how many, and to whom. Work happens in the dark.
- **Decision 2:** The win: the manager stops chasing people one by one for call updates — one live web dashboard answers "who called, how much" at any time.
- **Decision 3:** Two first users launch together on day one: the manager on the web dashboard and all 15-20 salespeople on the Android app. Success is judged by both — salespeople must adopt the dialer AND the manager must get real visibility.
- **Decision 4 (updated by Decision 91):** The manager is also the admin — the web role handles account creation, deactivation, delete, and the dashboard. The top manager keeps these powers for the whole company; a sub-manager only gets what the manager grants him. No separate admin role in v1.
- **Decision 5:** Outcome, in priority order: (1) the manager sees the team live — who called whom, how many, how long — without asking anyone; (2) every number is real — it comes from an actual call event on the phone and cannot be faked. The salesperson KPI dashboard is wanted but secondary to these two.
- **Decision 6:** Only calls dialed from our in-app dialer are tracked. Flow: dial from our app → log intent in local SQLite → after call ends, fetch exact time and duration for that call from the Android call log → sync to server → on success (200), delete the local entry. Calls from the normal phone dialer are NOT tracked — accepted limitation: a salesperson can bypass tracking by not using our dialer.
- **Decision 7:** The app tracks calls only. No GPS location, no attendance, no WhatsApp/SMS tracking, no chat — none of it in any early version unless a new decision says so.
- **Decision 8 (fetch updated by Decision 54):** v1 ships BOTH dashboards: the manager's team view and the salesperson's own KPIs (last 30 days, top 5 numbers, today/yesterday). No real-time in v1 — the manager's web dashboard fetches at login/refresh; the app's My Stats fetches on every tab open (Decision 54). Real-time (auto-refresh or push) is explicitly postponed to a future decision.
- **Decision 9:** The Android app is distributed by sideloading the APK (internal link or file share), not Google Play. This is what makes the call-log reading in Decision 6 possible — Play Store would reject the READ_CALL_LOG permission for a non-dialer app.
- **Decision 10:** Simplest architecture, three boxes only: (1) Mobile app in React Native — login, dialer UI, local SQLite queue, sync that deletes local rows on success, and the salesperson dashboard all live in RN; custom Kotlin is written ONLY as native modules for what RN cannot do — detecting when the call actually ends and fetching that call's exact time and duration from Android's call log — and only after checking existing RN libraries (e.g., react-native-call-log, call-state detection) so custom native code stays as small as possible; (2) one API server — login, account create/deactivate/delete, call ingestion made idempotent by a call ID so retries never duplicate, dashboard data endpoints; (3) manager web dashboard — team overview plus account management, served by the same API. No websockets, no message queue, no CRM, no location tracking — none survived the challenge. Each part follows the repo's existing style rules for its language. (Absorbs the old Decision 23 — same stack rule, recorded once.)
- **Decision 11 (updated by Decisions 50, 59):** Offline rule: while offline, call records wait in the local SQLite queue (Decision 53); a row is deleted only after the server answers 200, and every app open pushes all filled rows in one batch (Decision 29). Rows get filled two ways: the real-time listener fills them seconds after the call ends (Path 1, Decision 50), and the app-open janitor completes rows older than 1 hour that Path 1 missed — checks run only while the app is open, so a call from a phone closed all weekend still matches on the first open after reopening. Give-up rule (Decision 59 replaces the older delete rule): a row still empty after 5 janitor checks is FILLED — dialed_at = intent_at, duration_seconds = 0 — so the dial still rides sync and stays counted. The listener is not a background job — it is the app still running during the call it started.
- **Decision 12:** The app must work on any Android phone — the team's devices are unknown and not controlled. No device list exists; the tracking spike runs on the oldest phone the team actually uses.
- **Decision 13:** Consent happens through the app itself: it asks the salesperson for the call permission at runtime, and if the permission is off, the app shows a visible notice (toast or banner) saying calls are not being logged. No silent tracking.
- **Decision 14:** Both tracking parts are confirmed possible in React Native — reading the call history and detecting when the call ends — using existing libraries; if the libraries fail on real phones, we write our own Kotlin code for both, only if needed. Sources: [react-native-call-log](https://www.npmjs.com/package/react-native-call-log), [react-native-call-detection-android](https://classic.yarnpkg.com/en/package/react-native-call-detection-android), [call-end pattern](https://stackoverflow.com/questions/9684866/how-to-detect-when-phone-is-answered-or-rejected)
- **Decision 15:** Manager dashboard opens to team totals — today and yesterday: dials, connected calls, total minutes. Below the totals, one row per salesperson with the same numbers; tapping a person opens their individual view. Data loads on login/refresh — no real-time (per Decision 8).
- **Decision 16:** The individual view shows that person's counts (today / yesterday / last 30 days) plus the top 5 numbers by talk time — number and minutes. Red flags (one number with huge minutes, the same number every day) are spotted here by eye. No auto-flag rules and no graphs in v1.
- **Decision 17:** The dashboard counts dials and connected calls separately, plus total minutes. A 0-second unanswered dial counts as a dial only.
- **Decision 18:** "Software sold" does not appear anywhere on the manager dashboard in v1 — the approved screen design has four KPI cards only (Dials, Connected calls, Not connected, Talk minutes) and no placeholder card. Real sales tracking gets its own decision when wanted.
- **Decision 19:** Login is name + password (Decision 30 made the name the login ID — no username column). The manager creates each account (name, starting password). The app stays logged in after first login; a forgotten password is fixed by the manager setting a new one.
- **Decision 20:** The API server runs on Render (small paid plan, always awake) and the database is Neon's free Postgres — Singapore region on both, for low latency from India.
- **Decision 21:** Matching rule: each dial logs an intent row (number + time) in SQLite. After the call ends, the app matches the Android call-log entry with that number starting within 1 minute after the intent time (updated from "any time after" — agreed after grilling); two quick calls to the same number match in order (first intent → first entry). The tracking spike confirms the 1-minute window on the oldest real phone; the constant moves only if a real phone needs it (Decision 27). If the app is killed mid-call, the pending intent row is completed from the call log at the first app open after 1 hour — the janitor's job (Decisions 11, 50) — no new mechanism.
- **Decision 22 (updated by Decision 58):** Deactivated accounts keep their call history in the database and drop out of the team table while deactivated; their past calls keep counting in team totals (Decision 58). Reactivating brings them back with all numbers untouched.
- **Decision 24:** Standing rules: call times are stored in UTC and displayed as IST everywhere (the team works in one timezone); the calls table carries a unique index on the call ID so retried syncs can never double-count (Decision 10 made concrete).
- **Decision 25:** The dialer screen takes a number two ways: typed on the keypad, or filled with one Paste button press (a number copied from WhatsApp, SMS, or anywhere). No contact-list reading — the app asks for no permission beyond the call permission tracking already needs.
- **Decision 27:** Build order: the tracking spike comes first — prove the full chain (dial from our app → call ends → read the Android call log → match → exact duration) on the oldest phone the team actually uses (Decision 12) before building anything else. It is the only step with unknowns (Decision 14); the API and both dashboards after it are predictable work.
- **Decision 28:** Deleting an account is permanent: it removes the person, their auth token, and ALL their call rows — past team totals shrink and nothing comes back. Deactivate stays the safe option (history preserved, Decision 22). The web asks "this cannot be undone" before delete runs.
- **Decision 29:** Sync is one batch request: the app pushes every FILLED row in a single call (Decision 57 fixed "every queued row" to filled rows only); the server inserts each row and silently skips any call_id it already has (the unique index); on 200 the app clears the rows it sent. One code path for 1 call or 40.
- **Decision 30:** The server database is exactly three tables — users, calls, and leads — on Neon Postgres. No username column: login is name + password, so the manager must give every person a distinct name (updates Decision 19). The calls table stores only what dashboards use: call_id, user_id, phone_number, dialed_at (UTC), duration_seconds — no sync-timestamp column.
- **Decision 31:** Login sessions use an auth_token column on users: every login writes a fresh random token, the app and web send it with every request, and the server checks token + is_active before doing anything. Deactivate, delete, or a manager password reset kills old sessions instantly. No separate tokens table, no logout endpoint in v1.
- **Decision 32:** Display contract: the API returns talk time in seconds; screens show minutes (seconds ÷ 60, rounded). All today / yesterday / last-30-days boundaries are computed by the server in IST over UTC-stored times — screens never do date math. Connected is derived (duration > 0), never stored.
- **Decision 33:** Dashboard additions accepted: the team table is sorted by today's dials, highest first; the person screen shows connected % (connected ÷ dials); the top-5 numbers table shows a calls count beside minutes — Decision 16's red flags stay eyeball-only but get the numbers to do it.
- **Decision 34:** Every number is normalized to E.164 (`+919876543210`) by libphonenumber-js in the app. The default country for local-style numbers is per user — the manager picks it (ISO code like IN, AE, US) at account creation; nothing is hard-coded to India. It lives in a required `country` column on users and the login response returns it so the app knows what to assume. Numbers starting with `+` self-identify regardless. The same cleanup runs on the Android call-log number before matching (Decision 21's rule unchanged, its inputs cleaned). If parsing fails, raw digits are stored — a call is never lost over formatting.
- **Decision 35:** The sync server validates each batch row on its own: good rows are saved, a broken row is discarded with a log line, and the server still answers 200 so the app clears its queue. One corrupt row can never block good calls behind it (extends Decision 29).
- **Decision 36:** The manager edits a person through ONE endpoint — `POST /api/users/<id>/update` taking any of name, password, country. Password still kills the person's old token (Decision 31), name keeps the "That name is already taken" unique check (Decision 30), country is the dialing default (Decision 34). This makes a typo'd name fixable and a relocated person changeable without delete-and-recreate, which would lose their history (Decision 28). Deactivate, activate, and delete stay as their own endpoints — they are actions, not edits.
- **Decision 37:** Accepted limitation: `dialed_at` comes from the phone's clock. Phones normally auto-sync to network time, and the offline case needs phone time anyway — a weekend-off call must land on Saturday, not on sync day. A badly skewed clock could shift a call across a day boundary; accepted.
- **Decision 38:** The Accounts screen has its own read endpoint — `GET /api/users`, manager only. It returns every account (id, name, role, country, is_active), deactivated included, so greyed-out rows can be found and reactivated. Two lists, two jobs: this one manages accounts (no call numbers), the team dashboard (Decision 15) shows the numbers for active salespeople only. Call counts join the account list only if a future decision asks.
- **Decision 39:** The login response includes the user's own id. The app saves it at login and uses it as the `<id>` for My Stats (`/api/dashboard/person/<id>`, Decision 8) — before this, the app had no way to know its own id.
- **Decision 40:** Tracking needs THREE permissions, not one: CALL_PHONE (our app places the call), READ_CALL_LOG (the app reads the call log to match, Decision 21), and READ_PHONE_STATE (the real-time call-end listener, Decision 50). Android grants them separately, and the red banner shows when ANY one is off — checking only CALL_PHONE would hide the silent case where the call places fine but can never be recorded. The banner carries a Fix button that opens Android's settings page for our app; the person switches all three on there, and the next app check clears the banner. The real-time listener is react-native-call-detection-android (Decision 14) — custom Kotlin stays the last resort. (Absorbs the old Decision 51.)
- **Decision 41:** Permission work — checking, asking, and opening the settings page — uses react-native-permissions. Custom Kotlin stays the last resort, same rule as Decision 14.
- **Decision 42:** `connected_percent` comes back empty when the person has 0 dials in the last 30 days, and screens show "—" — "no data yet", not a 0% scolding (extends Decision 33).
- **Decision 43:** A deactivated person who logs in with correct credentials sees "Your account is not active. Please contact your manager." Only wrong credentials say "Wrong name or password."
- **Decision 44:** The call-log match accepts OUTGOING entries only. Android keeps outgoing, incoming, missed, and rejected in one call log, so "same number within 1 minute" alone (Decision 21) could match a customer calling back and record a call the salesperson never made. The rule is now all three: number matches (normalized), call_type is OUTGOING, entry within 1 minute after the intent. Outgoing calls have no "not connected" type — an unanswered dial is still OUTGOING with duration 0, which stays the only connected signal (Decision 17).
- **Decision 45 (updated by Decision 50):** The tracking spike (Decision 27) is an eight-case checklist, not just the happy chain: (1) normal answered call → duration is talk time, not ring time; (2) unanswered dial → duration 0; (3) a 3-minute ring before answer still matches inside the window; (4) two quick calls to the same number match in order; (5) an incoming call from the same number never matches (Decision 44); (6) app killed mid-call → the row completes at the first open after 1 hour, the janitor's job (Decisions 11, 50); (7) hang up → the real-time listener fires on the oldest phone (Decision 50); (8) after hang-up, measure the seconds until the call-log entry appears — Path 1 retries at 3s / 10s / 30s, then leaves the row to the janitor. All eight pass on the oldest real phone before anything else is built.
- **Decision 46:** No formal per-brand testing. The checklist (Decision 45) runs on one team phone; other brands are not pre-tested. If the dashboards ever show weird numbers for a person, the same checklist runs on that phone then. Accepted risk, revisited only when something looks wrong.
- **Decision 47:** Accepted limitation: the unsynced queue lives only on the phone, so a reinstall, cleared app data, or a replaced phone deletes unsynced calls forever — those calls never reach the server and the dashboards stay wrong for that window. Normal exposure is minutes (sync fires on every app open, Decision 11); loss needs offline days plus a wipe at the same time. No background sync — Decision 11's no-background-jobs rule stands.
- **Decision 48:** The server refuses deactivate and delete when the target is the manager's own account — with one manager (Decision 4) and permanent delete (Decision 28), one tap could otherwise lock everyone out. Edit (name / password / country, Decision 36) stays allowed on the manager's own account.
- **Decision 49:** Login limits guessing: after 10 wrong passwords for one name, that name waits 5 minutes before the next try. The counter lives in server memory — no new table. Names are not secret (they are the login ID, Decision 30), so without this, password guessing is unlimited.
- **Decision 50:** A call row is filled by TWO paths that never touch the same row at the same time. Path 1 (primary, real-time): at hang-up the call-end listener fires and retries reading the call log at 3s / 10s / 30s — the log entry can land a few seconds late, brand-dependent (spike case 8) — then fills dialed_at + duration; sync sends it, and if the background send dies the filled row simply waits for sync-on-open. Most calls are recorded in seconds. Path 2 (safety net, the janitor): on every app open, rows older than 1 hour that are still empty get completed from the call log or given a strike — no real sales call lasts an hour, so anything still empty at 1 hour is a call Path 1 missed (app killed mid-call, listener died). Young rows are never the janitor's, so there is no race; the 5-strike give-up (Decision 11) lives only in the janitor. Worst case is a call recorded late, never a call lost.
- **Decision 52:** With CALL_PHONE off, our app cannot start a call — Android's rule, not ours. The Call button then hands the number to the phone's own dialer (one extra tap there), and that call is NOT tracked: no intent row is written. One rule: permission off = not tracked. The red banner is the real protection; this fallback exists only for a person who ignored it.
- **Decision 53:** The phone's only local database is the pending-calls queue — a SQLite table `pending_calls`: call_id (created the moment Call is tapped), phone_number (normalized at dial time, Decision 34), intent_at (phone clock at tap), dialed_at + duration_seconds (EMPTY until a path fills them from the call log, Decision 50), attempts (strike counter, janitor only). Empty duration = still waiting, filled = ready to send — no status column. My Stats keeps no local copy (Decision 54), so this queue is the phone's one and only table.
- **Decision 54:** My Stats hits the API directly: every tab open calls `GET /api/dashboard/person/<own-id>` (Decision 39) and shows the answer. No local stats copy and no local counting — the server stays the single accountant (Decision 32), so his screen and the manager's screen can never disagree. Updates Decision 8's fetch wording; "no real-time" (Decision 8) still stands.
- **Decision 55:** "App open" is ONE event: the app comes to the foreground — tapping the icon, or returning to it after a call or from another app. No cold-start vs foreground-return split, no special case (raised and rejected as an unneeded edge case) — one code path. The open sequence always runs the janitor FIRST, then sync: rows the janitor completes or strikes (Decision 50) are ready before the batch send (Decision 29), so calls recovered on that open ride the same batch instead of waiting one full extra app open. Sync has exactly TWO triggers — app open (after the janitor), and immediately after a row is filled (Decision 50's Path 1) — both send the same one batch request, both happen while the app is in the foreground, so Decision 47's no-background-sync rule stands.
- **Decision 56:** Phones are personal — one person, one phone, and a phone never moves to another person, so the queue can never sync under the wrong login. Escape hatch for the rare exception (a swapped or corrupted queue): the app gets a **Clear local data** entry — a small gear icon on the My Stats header opening a one-item settings screen. It wipes only the `pending_calls` queue, after asking: "This deletes N calls not yet sent to the server. Cannot be undone." Nothing on the server is touched. This replaces "reinstall the app" as the recovery path (extends Decision 47).
- **Decision 57:** Sync sends FILLED rows only. A row with an empty duration has nothing real to store — no `dialed_at`, no duration (Decision 53) — so the batch picks up completed rows and leaves empty rows waiting; the janitor fills them at the 1-hour mark and they ride the next sync (Decisions 29, 50, 55). Nothing is lost and nothing fake is sent. Fixes the wording clash between Decision 29's "every queued row" and Decision 53's "filled = ready to send."
- **Decision 58 (updates Decision 22):** Deactivation stops the person, not the numbers. While deactivated, no new call can arrive from them — the server's token + is_active check rejects their app (Decision 31), and login is blocked (Decision 43) — but every call that already reached the server keeps counting in the team totals exactly as before: today's number never drops when someone is deactivated. The team table still lists active people only, so the total can be larger than the sum of the visible rows — accepted: the total is "everything that happened today," the table is "who is on the team." Reactivating brings the person back with all numbers untouched, and their phone's leftover queue syncs again (phones are personal, Decision 56). Only DELETE removes calls (Decision 28). A deactivated person's history stays reachable: tapping their row on the Accounts screen opens their person view (the Accounts list itself still carries no call counts, Decision 38).
- **Decision 59 (updates Decision 11):** The 5-strike rule fills the row instead of deleting it. An orphan row with no call-log entry after 5 janitor checks gets dialed_at = intent_at (the tap moment — the only real time we have, Decision 37) and duration_seconds = 0 — a filled row that rides the normal sync (Decision 57), so the dial reaches the server and stays counted. Why: the intent row proves a real dial — a fake one costs a real call — so deleting turned "duration unknown" into "call never happened," which broke Decision 5 and left no trace for Decision 46's "weird numbers" check. Accepted cost: 0 means "not connected" (Decision 17), so a rare connected call whose log entry vanished shows as a dial with no connection — dials stay exact, connected and minutes are short only by these rare rows.
- **Decision 60:** The Android app is bare React Native CLI, no Expo. The three native-code libraries (call-log read, call-end listener, permissions — Decisions 14, 41, 51) plug in directly, and the sideloaded APK is a plain Gradle build (Decision 9). Expo's managed workflow hides the Android folder these libraries need.
- **Decision 61:** Automated tests live in the API only — pytest covering login and the lockout (Decision 49), sync skipping duplicate call_ids and broken rows (Decisions 29, 35), IST day boundaries over UTC times (Decisions 24, 32), and totals across deactivate/delete (Decisions 22, 58). The spike checklist (Decision 45) is the app's test; the web dashboard is display code with no logic worth testing in v1.
- **Decision 62:** The team table always lists every active salesperson, zeros included — the manager's core question is who is NOT calling (Decision 1), and hiding zero-call rows would hide the answer.
- **Decision 63:** The web dashboard keeps its token in localStorage — the manager stays logged in across refreshes, matching the app's stay-logged-in rule (Decision 19). A dead token (Decision 31) gets a 401 and the login page — the same contract as the app.
- **Decision 64:** When the server is unreachable, stats screens show one short message — "Can't reach the server. Check your internet." — and no numbers, never fake zeros. No offline copy of stats (Decision 54); the next open or refresh retries. The dialer and the pending_calls queue keep working offline regardless (Decision 11).
- **Decision 65:** Every screen — app and web — is English only in v1.
- **Decision 66:** Starting passwords need at least 8 characters with at least one uppercase and one lowercase letter; no other rules. The web form and the API both check it (the API is the real gate). Decision 49's lockout stays the anti-guessing defense.
- **Decision 67:** All date math, period bucketing, and aggregation happens on the server; screens never touch dates or periods. Screens may do display-level division on returned aggregates only: seconds ÷ 60 for minutes, hour totals ÷ 30 for the daily average, period totals ÷ active_days for per-active-day averages, dials − connected for not connected, and percentage-change comparisons against a returned yesterday. The person endpoint returns `connected_percent` inside each period (today, yesterday, last_30_days).
- **Decision 68:** The APK gets one release signature keystore, created once and kept safe forever — every future update must use the same stamp (Decision 9). The user creates it by hand when app building starts; it gates the first sideloadable build and is a manual step in the task list, not an automated one.
- **Decision 69:** The web dashboard is manager-only. Its URL is never shared with salespeople. If a salesperson logs in on the web anyway, the web routes by role and shows one message — "This dashboard is for managers." — and no data. The login endpoint itself stays shared (Decision 8's app/web login).
- **Decision 70:** The country dropdown (Decision 34) is a shortlist, not every country — it starts with IN, AE, US and grows with one line of code when the team needs another.
- **Decision 71:** Backups rely on Neon's native restore only — nothing custom in v1. Free-plan facts: point-in-time restore reaches only the last 6 hours, there are no automatic backups, and the plan includes one manual snapshot that never expires. Standing habit: after any big manual change in the Neon console (bulk delete, schema change), take the manual snapshot — one click, replaces the old one.
- **Decision 72:** The app's name on the phone is "Apex Sales Call".
- **Decision 73:** The Call button locks the moment it is tapped and unlocks when the dialer takes over — one tap = one intent row (Decision 53). A double-tap can never create a second intent for one real call that Decision 59 would later fill and count as a dial that never happened.
- **Decision 74:** The manager never uses the Android app — the web is the manager's only workplace. The app has no manager mode: it treats every account the same, so even a manager logging in there is just another dialer user.
- **Decision 75:** The tracking spike (Decision 27) is built to grow into the real `app/` folder — the proven permission, call-log, and matching code ships instead of being thrown away. Getting the oldest team phone (Decision 12) physically in hand is a manual task-list step, arranged before the spike starts.
- **Decision 76:** Accepted oddities, on the record: a salesperson can inflate dials with junk calls (exposed by Connected %, symmetric to Decision 6's bypass); two phones on one login stall the first phone until re-login (Decision 56's personal-phones rule); Neon free sleeps after quiet periods so the first load after one may be slower; the login lockout counter (Decision 49) lives in server memory, so a server restart clears it — one Render instance only.
- **Decision 77 (updated by Decision 91):** The manager's create-account form offers two roles — Salesperson and Sub-manager. Only the top manager can create sub-managers; no second top manager can be created in v1.
- **Decision 78:** No password self-service: only the manager sets and changes passwords (create + edit endpoints). A salesperson who wants a new password asks the manager. Accepted limitation, kept beside Decision 76's oddities.
- **Decision 79:** The code lives in a private GitHub repo connected to Render — every push to main auto-deploys the API and the web dashboard it serves. One-time setup, then deploys are free. The repo starts with zero commits today.
- **Decision 80:** Calls are kept forever — no retention or cleanup job in v1. At this team's size the calls table stays tiny for Neon's free plan.
- **Decision 81:** App icon: a free placeholder icon from the internet for now; the final icon gets its own later decision. The name stays "Apex Sales Call" (Decision 72).
- **Decision 82:** Minutes rounding is display-only and applies ONLY to sums — the database and API always keep exact seconds (extends Decision 32). Screens round totals to the nearest minute, and any total with at least 1 second shows at least "1 min". No screen shows an individual call in v1; when a call-log screen comes later, each call shows its exact duration ("38 sec" / "1:12"), never rounded minutes.
- **Decision 83:** The file tree follows `structure.md`: `backend/` uses a modular monolith architecture per `python-flask-code-style.md` with feature modules under `app/modules/` (auth, calls, dashboard, users, leads); `web/` uses React + TypeScript with feature folders (`src/features/`); `app/` uses bare React Native CLI + TypeScript with feature folders. Flask serves the built web dashboard from `web/dist` through one catch-all route — same server, same origin, so no CORS and no API URL config for the web.
- **Decision 84:** Both React codebases have real shared components from day one (no empty folders). The web has no top navbar: the sidebar carries the product name, the MENU links, and Logout at its bottom, and each page renders its own slim top bar with the page title. Logout is browser-side only: clear the saved token, show the login page — no endpoint, so Decision 31's "no logout endpoint" stands. The app's 12-key Keypad component is pulled out of the dialer screen the same way.
- **Decision 85:** `app/config/base.py` holds every named constant in one place: `MAX_CALL_AGE_DAYS` (Decision 86), the lockout (10 tries / 5 minutes, Decision 49), the password rule (8+ characters, upper and lower, Decision 66), the IST timezone name (Decisions 24, 32), and the country shortlist (Decision 70). No magic numbers anywhere.
- **Decision 86:** The server accepts only calls from the last `MAX_CALL_AGE_DAYS = 3` days. The check runs on the server per row at sync, on the call's real time (`dialed_at`): older rows are dropped with a log line, and the server still answers 200 so the app clears them (Decision 35's per-row pattern). Accepted loss, on the record: a phone offline longer than 3 days loses everything older — including the orphan dials the janitor filled (Decision 59); those calls never count.
- **Decision 87:** The Call button unlocks only when libphonenumber-js says the typed number is valid for the logged-in person's country (Decision 34) — for India that means exactly 10 digits, or a full +91 number; pasted numbers pass the same check (Decision 25). A number the library cannot validate cannot be dialed — the person fixes or retypes it.
- **Decision 88:** Paste with an empty clipboard does nothing to the number field — a small toast says "Nothing copied." and any typing stays untouched.
- **Decision 89:** Sync accepts any active token (Decision 31) and saves each row under the token owner's id — no manager-role guard. The manager never uses the app (Decision 74), so the case never occurs in practice; "each call belongs to whoever's token sent it" is the simplest always-true rule.
- **Decision 90:** The API uses Flask-SQLAlchemy instead of raw SQL — chosen with the SaaS road in mind: as tables grow toward a multi-tenant product, schema changes and queries get easier. The `users`, `calls`, and `leads` tables are defined as SQLAlchemy models in `app/modules/users/models.py`, `app/modules/calls/models.py`, and `app/modules/leads/models.py`, mapping to the same Neon Postgres tables. The class-based model is the one accepted exception to the repo's functions-only rule (an ORM model is a data definition, not logic); every other layer stays functions-only. psycopg2-binary stays in requirements.txt as the driver underneath, and the app config carries `SQLALCHEMY_DATABASE_URI` from the DATABASE_URL env var.
- **Decision 91:** Teams and sub-managers are v2 work. The v2 shape: ONE top manager; under him, sub-managers can each own a team. A sub-manager sees only his own team's numbers on the web dashboard; the top manager sees everything, all teams. A sub-manager can never remove or edit the top manager; the top manager can remove sub-managers. WhatsApp + auto-next stay lower-priority wants.
- **Decision 92:** A v2 rule for sub-managers: the manager grants team power per sub-manager with a switch on the create/edit form: "can manage his team". On — the sub-manager adds salespeople and deactivates/reactivates them inside his own team. Off — he only sees his team's numbers. Delete and edit stay top-manager-only in both cases.
- **Decision 93:** A v2 rule for teams: the manager must create teams first — as many as he wants (the client runs multiple products and will likely ask for more teams later), and every salesperson sits in a team. Assigning a sub-manager is the only optional part: a team can run with no sub-manager, at most one per team. Inside a team the manager sees everything — people, sub-manager, numbers. Manager and sub-manager see the SAME team dashboard screen; every salesperson's numbers always reach the top manager, and also the team's sub-manager when one exists. A sub-manager can never create teams.
- **Decision 94:** v1 ships a lead flow: the manager uploads a CSV of phone numbers on the web, the numbers land in one shared pool, and salespeople call the leads from the app — one tap per call, nothing dials by itself. All call tracking works exactly as already decided. Interested / very interested labels are v2.
- **Decision 95:** The lead CSV holds ONE column — phone numbers only. No names, no extra fields.
- **Decision 96:** The pool is shared: any salesperson's "next call" gets the next available lead, and whoever taps first gets it. An unconnected lead that comes back after its 2-hour lock is available to any salesperson again — only scheduled leads are reserved to one person.
- **Decision 97:** A lead's life: a connected call finishes it — done, out of the flow forever. An unconnected call sends the lead back to the shared pool with a 2-hour lock (config `RETRY_LOCK_HOURS`); after the lock, any salesperson's "next call" can get it. After 3 failed attempts (config `MAX_LEAD_ATTEMPTS`) it is stopped and never surfaces again. Both constants live in `app/config/base.py`.
- **Decision 98:** A salesperson can schedule any lead that is neither done nor stopped: they pick a date and time, and the lead is reserved for them — no other salesperson's "next call" can serve it. At that time it shows at the top of their own Leads tab and stays there until it is called.
- **Decision 99:** Newest leads first: "next call" serves the newest available lead. Older leads wait cold at the back of the pool and surface only when nothing newer is available.
- **Decision 100:** A lead handed out by "next call" is claimed for 10 minutes (config `CLAIM_MINUTES`). When the claim passes without a call, the lead simply becomes available again — so two salespeople can never dial the same lead at once.
- **Decision 101:** A manual keypad call counts for the pool too: if the dialed number, normalized, matches a waiting lead, the call updates that lead like any lead call.
- **Decision 102:** A lead's state lives on its own row — status (waiting / done / stopped), attempt count, last-attempted time, claim fields, schedule fields. Nothing about a lead is computed from the calls table on the fly.
- **Decision 103:** Upload rules: the manager picks the country for the upload (IN, AE, US — the same shortlist), and every number is normalized to E.164 with Python's phonenumbers library. Duplicate numbers inside the file, numbers already in the pool in any state, and rows that cannot be parsed are all skipped and counted. The upload result reads "N added · N duplicates · N invalid."
- **Decision 104:** The salesperson app focuses on dialing and calling leads: Dialer (keypad for manual dialing) and Automated (lead-calling flow: a Start calling button brings up the next lead as a card with Call and Schedule; after each call the card flashes the result — Connected or Not connected, read from the phone's own call record, never typed by the salesperson — and the next lead appears automatically). Salespeople do not have an overview screen of pool counts or a schedule cancellation interface.
- **Decision 105:** The web gains one Leads page for the manager: the upload, four pool counts (Waiting now, Scheduled, Connected, Stopped), and a per-person table for today — attempted, connected, not connected.
- **Decision 106:** The tracking chain is untouched by leads: intent rows, call-log matching, batch sync, the janitor, the three permissions — a lead call is an ordinary tracked call. At sync, the server matches each saved call to a waiting lead by normalized number: connected makes the lead done; unconnected adds a failed attempt and sends the lead back to the pool for its 2-hour lock; the lead stops at the cap; the schedule fields clear when a lead resolves.
- **Decision 107:** Leads get their own pytest file, tests/test_leads.py, covering: the upload skips (duplicates, already-in-pool, unparseable), newest-first serving, the claim window, the 2-hour lock, the attempt cap → stopped, connected → done, schedule reservation to the right person, and the summary counts.
- **Decision 108:** A connected call finishes the lead even when the person on the phone asked for a call-back — "call me tomorrow" cannot be booked after the call, because the Schedule button works only on leads that are not done. Accepted v1 limit, on the record: follow-up scheduling after a connected call arrives together with the v2 interest labels.
- **Decision 109:** A release rolls back by putting the old code back on GitHub — Render auto-deploys the old version. The leads table is additive: an empty table left behind by a rollback is harmless and is dropped later only if wanted.
- **Decision 110:** Scheduled times are future-only: a time in the past is refused, the picker offers future dates only, and the chosen time may sit at most one month ahead — past that the server refuses. The one-month limit lives in config.py as MAX_SCHEDULE_AHEAD_DAYS = 30. The picker opens on the phone's IST time; the app converts to UTC before sending, so storage stays UTC.
- **Decision 111:** The lead upload refuses files over 2 MB with the plain message "File is too large." — the small Render plan must never try to swallow a huge file. The limit lives in config.py as MAX_LEAD_UPLOAD_MB = 2.
- **Decision 112:** The API response convention for mutation endpoints (sync, user create, update, activate, deactivate, delete) returns `{"status": true}` on success, and `{"message": "..."}` on error.
- **Decision 113:** The automated calling loop uses a unified endpoint `POST /api/leads/next` that can optionally schedule the current lead and claim the next available lead in a single network request, ensuring every call transition takes only one network hit.
- **Decision 114:** The lead upload endpoint `POST /api/leads/upload` returns `{"status": true, "added": N, "duplicates": N, "invalid": N}` without a text message string.
- **Decision 115:** Salespeople do not have a lead pool overview screen or a schedule cancellation endpoint. The automated calling loop handles all lead serving and scheduling directly.
- **Decision 116:** Database initialization uses Flask-SQLAlchemy `db.create_all()` on startup, and the initial manager account is created automatically from the `MANAGER_NAME` and `MANAGER_PASSWORD` environment variables — no CLI seed command exists. Because the database is greenfield with no prior data, no data migration steps are required.
- **Decision 117:** Emergency rollback for the database drops tables using CASCADE (`DROP TABLE IF EXISTS leads, calls, users CASCADE;`), cleanly removing tables and foreign key constraints without residual locks.
- **Decision 118:** The initial manager account is created automatically when the server starts: the server reads `MANAGER_NAME` and `MANAGER_PASSWORD` from the environment (loaded from the root `.env` via python-dotenv) and creates the manager if no user with that name exists. If either value is missing, the server refuses to start with one clear message — no hardcoded fallback password exists anywhere. The old `flask seed` CLI command is removed. Bootstrap is skipped under the test config so tests keep building their own users.
- **Decision 119:** The approved screen screenshots are the web's visual source of truth: indigo primary color on a lavender page background, a white sidebar (brand with phone icon on top, MENU label, Dashboard / Team / Leads / Accounts / Settings links, Logout at the bottom, icon-only rail on mobile), and a slim per-page top bar with the page title. All five web screens — Login, Team Dashboard, Person View, Leads, Accounts — are rebuilt to match them.
- **Decision 120:** The Dashboard carries: a Today | Yesterday | 30 days pill switch; four KPI cards (Dials, Connected calls, Not connected, Talk minutes) with per-active-person-per-day average sub-lines; a Calls-by-hour bar chart with the best hour highlighted and a summary line under it; and a Top 5 by minutes people list. No person rows appear on it.
- **Decision 121:** The Person View carries: an initials avatar beside the person's name; four KPI cards for the last 30 days (Active days out of 30, Avg dials, Avg connected, Avg minutes — averages per active day, with the period totals as sub-lines); the three-period performance table; and the most-contacted-numbers table.
- **Decision 122:** The Leads page carries: two daily KPI cards (Leads Uploaded and Leads Tackled, each compared against yesterday with a percentage change); the Active Lead Pool card with five stage cards (Waiting with 0, 1, and 2 calls, Scheduled, Stopped) and a colored pool-composition bar; and the per-person table for today below the pool card.
- **Decision 123:** Web popups use the sonner toast library. A successful lead upload shows a floating toast carrying the added / duplicates / invalid counts; the in-dialog result panel is removed and the dialog closes on success.
- **Decision 124:** The Accounts list shows an accounts count ("8 accounts · 7 active") in the card header and a "You" badge on the manager's own row. The Accounts page has no Back link — it is a top-level page; the Person View keeps its Back link.
- **Decision 125:** The Calls-by-hour chart is drawn with Recharts — the catalog's chart library and the one shadcn/ui builds its charts on. A period with zero calls shows a short "No calls in this period." note instead of an empty chart frame, and the best-hour highlight is hidden.
- **Decision 126:** The new display edge cases are settled: a chart period with zero calls shows the empty note; a zero yesterday hides the percentage pill on the Leads daily cards; a person with zero active days shows "—" in all four average cards; the team table scrolls horizontally inside its card on narrow screens.
- **Decision 127:** The whole web dependency set upgrades to current stable in one install — React 19 line, Vite 8 line, and every library bump together — because the pieces pin each other (the Vite React plugin requires Vite 8, and the current UI libraries require React 19). npm's peer-range check at install is the final compatibility gate. The Tailwind v4 build removes `web/tailwind.config.js` and `web/postcss.config.js` in favor of the `@tailwindcss/vite` plugin and a CSS `@theme` block; `tw-animate-css` restores the dialog animations the old setup silently lacked.
- **Decision 128:** The web and backend halves of the mockup-matching work ship together in one push — Render deploys the API and serves the rebuilt web from the same repo. Every API change is additive, so the old web keeps working against the new API during the deploy window. Rolling back means reverting the release commit on GitHub; Render auto-deploys the old version and the additive fields left behind are harmless.

## Round 2

- **Decision 129:** All dashboard math moves to the backend — the web frontend renders only what the API returns: it adds %, +, commas, "10 AM" hour labels, and card wording, but computes no number (no percents, no averages, no deltas, no best hour, no ÷30, no seconds-to-minutes).
- **Decision 130:** Dashboard responses use a per-period shape — each period object (today, yesterday, last_30_days) carries its own totals, calls_by_hour, and top_people, because every screen shows one period at a time.
- **Decision 131:** The team dashboard response drops the `people` list — salesperson rows come from a future separate Team section with its own endpoint; the backend still counts active salespeople internally to compute the per-person averages.
- **Decision 132:** Office hours is one manager-editable window stored in the database, default 10:00–19:00 IST, set from a small editor in the manager Settings screen, and it applies to every day of the week — Sunday included. The window shape is start and end time only; there is no working-day rule.
- **Decision 133:** The office-hours gate runs at call sync: a synced call is kept only when its IST start minute falls inside the window, both ends inclusive (18:59 ✓, 19:00 ✓, 19:01 ✗, 9:59 ✗, 10:00 ✓). Outside calls are discarded with a warning log like the other rejects, so no dashboard query needs an office-hours filter. The call's start time decides — not the sync moment.
- **Decision 134:** No retroactive cleanup — calls stored before the gate keep counting in totals; the calls-by-hour chart simply has no bucket for their hours. Only newly synced calls are gated.
- **Decision 135:** Manager and salesperson both get the calls-by-hour chart — the person dashboard response gains `calls_by_hour` per period and the person page renders the same chart component.
- **Decision 136:** The Android app is unchanged — it keeps syncing exactly as today; the gate lives server-side, and refused calls simply never appear for the admin or the salesperson.
